# AI利用レポート

## 使ったもの

| 用途                           | ツール      |
| ------------------------------ | ----------- |
| 調査・レビュー・文書・設定整備 | Claude Code |
| 実装・リファクタリング         | Codex CLI   |

## 進め方

1. **仕様から始める。** 課題READMEとAPI仕様を読み、PRD・設計・デザインを先に作り、受入条件を決めてから実装に入った。
2. **小さなPRで積み上げる。** 1機能・1部品ごとにIssueとPRを切り、PRテンプレートに「何が変わるか・画面の変更・確認結果・プレビュー確認」を書いて人間がレビューしやすいように開発フローを構築。
3. **人間が判断する点を分ける。** APIキーの入力、Cloudflare・GitHubの認証やSecrets登録、本番公開、デザイン判断は人間が行い、AIには値を渡さない運用にした。

## 成果として挙げられるもの

短い時間で、アクセシビリティ検査や Core Web Vitals の計測まで含めた、先を見据えた AI 駆動開発の土台を効率的に作れたことが最大の成果です。機能の実装だけでなく、以後の変更を安全に積み上げるための検証・計測・文書の仕組みを短時間で整えました。

- **3層のテストとアクセシビリティ検査。** 単体（Node）・Vue部品（jsdom）・Chrome実機（Playwright）の3層で221件＋114件。axe（WCAG 2.2 AA）をPRごとのCIで実行し、カバレッジは行94%。
- **Core Web Vitals の計測。** PRごとに静的UIのPreviewを公開し、Lighthouseで PC・モバイルの LCP・CLS・TBT を計測して結果表をPRコメントに返す。性能の退行をレビュー時点で見られる。
- **文書と実装の整合性レビュー。** 全文書を実装と突き合わせ、矛盾・陳腐化・未記載を一覧化して整理した

## 注意したこと

- **見た目をスクリーンショットとプレビューで必ず確認する** 見た目が追加および変更になる際には、PRにスクリーンキャプチャを添付し、PRに紐づくプレビュー環境を用意することで人間が確認しやすいような仕組みにした。
- **AIの出力は必ず検証する。** 調査結果は実ファイルで裏取りし、修正はlint・型・単体・E2E・buildを通してからPRにした。AIが出した「リンク切れ」の指摘が誤検知だった例もあり、ツールの結果をそのまま採用しないようにした。
- **秘密情報を渡さない。** APIキー・トークンは本人だけが扱い、AIが読むファイルや出力に値が出ないよう手順を組んだ。
